## Previous checkpoint — 2026-09-15 (batch C), inventory + reversible movement persistence
- Task 4. `app/api/inventory/route.ts` previously kept movements in a module-level `let movementsLog = [...]` array (reset to hardcoded fixtures on every server restart) and `app/inventory/page.tsx` used a hardcoded `INITIAL_PRODUCTS`/`INITIAL_MOVEMENTS` array (`setTimeout`-simulated writes, never persisted). Both replaced with real storage against the existing `products`/`inventory`/`inventory_movements` tables (schema already present in migration 001; migration 002 already seeds the real 31-product catalog with cost/retail/sale prices, excluded here as company data per existing convention, same as for customers/orders).
- New `supabase/migrations/008_inventory_persistence.sql`: `business_inventory_catalog`/`_movements`/`_movement_document` (reads) and `business_inventory_movement_create`/`_movement_reverse` (writes), same idempotent/advisory-locked/least-privilege style as migrations 006/007. `inventory_movements.quantity` is used exactly as the existing schema comment already specified ("positive for increase, negative for decrease") — no new columns, no schema reinterpretation.
- Correction model is **additive, never destructive**: a movement is never edited or deleted. "Reversing" a movement inserts a new movement with the exact opposite signed quantity, linked back via `reference_type='reversal'`/`reference_id=<original id>`. A reversal cannot itself be reversed, and the same movement cannot be reversed twice — both enforced in SQL, not just the UI. Stock is guarded so it can never go negative (`INSUFFICIENT_STOCK`), covering both direct movements and reversals.
- `lib/business-server.ts`: added `prepareInventoryMovement` (SKU/type/quantity validation, server-derives the signed delta — purchase_in/return_in positive, sale_out/damaged negative, adjustment takes an explicit `direction`) and `prepareInventoryReversal`. `lib/business.ts`: added `BusinessProduct`/`BusinessMovement` types.
- `app/inventory/page.tsx` rewritten to load real data (`loadBusiness`), post movements through the same idempotent retry-safe `saveBusiness` helper used by orders/finance/customers, and added a "reverse" action per movement row (disabled once a movement already has a reversal). Removed several pieces of fabricated UI copy that no longer matched reality now that real data is used (hardcoded "31 products across 6 lines", fake per-rep customer counts in a filter dropdown were already removed in the customers batch) — category pills, low-stock banner text and header counts are now all computed from the real catalog.
