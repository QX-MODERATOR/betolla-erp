# Orders and collections migration review

Apply `005_payment_methods.sql` and commit it before `006_business_persistence.sql`, first in a disposable/staging Supabase project with the existing schema. Neither migration has been applied to a remote database in this batch. The application needs the existing server-only `SUPABASE_SERVICE_ROLE_KEY` and `NEXT_PUBLIC_SUPABASE_URL`. Missing configuration/schema returns an explicit error, never demo data or successful saving.

006 adds order ownership/snapshots, item price provenance, an ownership index, the request ledger and five private RPCs. Existing orders, items, invoices, payments and policies are retained. Each create request atomically inserts customer (unless an explicit existing ID was supplied), order, items, invoice and request record. No phone-based customer merge is attempted. Finance derives payments from the ledger, including existing payments. Unpriced WhatsApp lines remain explicitly unknown rather than being displayed as free. New structured orders require the declared total to reconcile to priced lines; this batch does not introduce discounts or delivery-fee editing.

Only the server service role can execute the RPCs. The API reuses the existing role checks. Representatives read/change orders carrying their canonical account ID; older rows without this new owner field remain visible to roles with global order access. Mapping legacy `rep_id` UUIDs to the existing application account IDs needs verification before rollout; do not infer ownership from customer names. Current authentication/password behavior was not changed.

Collections lock the order and invoice, sum posted payments, reject excess amounts, insert the receipt and update payment statuses in one transaction. Request keys survive an uncertain client response in per-account sessionStorage; confirmed business records always come from the database. Digital transfers additionally require a unique normalized method/reference across invoices. Keep the original browser tab/session when resolving an uncertain cash collection; cross-device recovery without its original request key is not established. Status transitions use the previous state as a concurrency check. Return/cancellation disables further collection and exposes previously collected money as a customer credit; refund posting and stock movements remain separate work. Drag ordering is explicitly temporary presentation order.

## Verification and rollback

Install only the disposable test engine with `npm install --prefix .local-tests --no-save --package-lock=false --ignore-scripts @electric-sql/pglite@0.5.8`, then run `node scripts/test_business.mjs` and `node scripts/test_business_client.mjs`. These scripts never load dotenv and replace credentials/URLs with fixtures and a loopback RPC bridge. They execute the actual SQL and route handlers, test legacy balance retention, rollback, duplicates, lost responses and close/reopen durability. The baseline's two unused extension declarations are omitted and a stub `auth.users` table stands in for Supabase Auth. PGlite serializes its connection; Promise.all request tests do not prove independent PostgreSQL-session lock contention. Hosted PostgREST/RLS configuration and actual browser/mobile behavior still require staging verification.

Rollback before usage: revert application code and leave the additive schema/enum values in place. After any usage: stop order/payment writers and retain all new tables, columns and receipts; never drop the request ledger or re-enable the old in-memory finance UI as a working financial source. A rollback to older readers must be reconciled against retained invoices/payments before operations resume. No data deletion or production migration is authorized here.
